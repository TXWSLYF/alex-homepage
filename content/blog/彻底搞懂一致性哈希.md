缓存从 4 台扩到 5 台，为什么大约 80% 的 key 都换了一台机器？把服务器画成一个圆之后，负载不均、机器权重不同、一份数据要放多份，又该怎么处理？

这篇文章按一条主线展开：**为什么少搬家 → 哈希环怎么归属 → 虚拟节点与再平衡 → 权重和副本**。

---

## 1. 为什么用一致性哈希

节点名单会变时，取模会让绝大多数 key 改道。哈希环把每台机器收成一段弧，增减机器只改相邻的那段。

### 1.1 取模一扩容就大搬家

节点数固定时，`hash(key) % N` 够用：哈希够散的话，每台大约拿到 `1/N`。节点从 `N` 变成 `N + 1`，而且新节点排在名单末尾，一个 key 留在原机器上，当且仅当两个余数相同。留下来的比例是 `1/(N+1)`，搬走的比例是 `N/(N+1)`。

| 扩容 | 期望留下 | 期望搬走 |
| :--- | ---: | ---: |
| 3 → 4 | 25% | 75% |
| 4 → 5 | 20% | 80% |
| 9 → 10 | 10% | 90% |

> **核心结论：** 取模把节点身份绑在「除以几」上。除数一变，身份就变。一致性哈希要保住的是另一件事：key 只在旧主人和新邻居之间移动，已经在服务的机器不会互相抢 key。

### 1.2 哈希环

把哈希空间收成一圈。生产里常见 `0 .. 2^32 - 1`，最大位置的下一个是 `0`。为了能手算，下面用 `[0, 100)`。

| 机器 | 落点 |
| :--- | ---: |
| cache-a | 20 |
| cache-b | 50 |
| cache-c | 80 |

从 key 的落点顺着数字增大的方向走，遇到的第一台机器就是主人。正好踩在落点上的 key，归这台机器。

| 机器 | 拥有的位置 | 弧长 |
| :--- | :--- | ---: |
| cache-a | `(80, 100)` 和 `[0, 20]` | 40 |
| cache-b | `(20, 50]` | 30 |
| cache-c | `(50, 80]` | 30 |

```text
0 -----> 20 -----> 50 -----> 80 -----> 100(=0)
       cache-a   cache-b   cache-c

cache-a 还拥有 80 之后、绕回 20 的那一段。
```

| key 的落点 | 主人 |
| ---: | :--- |
| 5 | cache-a |
| 20 | cache-a |
| 35 | cache-b |
| 60 | cache-c |
| 90 | cache-a |

环只是一种排法。有用的是每台机器拥有一段连续的弧。第 2 节处理两件随之而来的事：弧长不均，以及机器增减时谁该搬家。

## 2. 环上的均匀与再平衡

一台机器只占一个点时，弧长随落点起伏。虚拟节点把弧切碎再拼回去。节点加入或离开时，只有被切开的那段弧换主人。

### 2.1 虚拟节点

第 1 节的三段弧已经是 40、30、30。机器更少、落点更挤时，一台机器可以占掉大半圈。

每台物理机器用 `机器名#0`、`机器名#1` … 各自哈希出多个点。查找时先找到顺时针的下一个点，再映射回物理机器。

```text
A 的点：  A0      A1        A2
B 的点：     B0       B1   B2

环： --A0--B0--A1--B1--B2--A2-- （然后绕回去）
```

A 不再拥有一整段长弧，而是拥有很多小弧的并。点越多，弧长越接近均匀；`N` 台机器、每台 `V` 个点，查找是对 `N * V` 个有序点做二分。缓存客户端常见的起点是每台 100 到 160 个点。

虚拟节点摊开的是 key 的个数。同一个 key 的全部请求仍然打在同一台机器上。

### 2.2 节点加入或离开

沿用第 1 节的三台机器。

**cache-b 下线。** 它的弧 `(20, 50]` 交给顺时针下一台 cache-c。cache-c 改为拥有 `(20, 80]`。

| key 的落点 | 之前 | 之后 |
| ---: | :--- | :--- |
| 5 | cache-a | cache-a |
| 20 | cache-a | cache-a |
| 35 | cache-b | cache-c |
| 60 | cache-c | cache-c |
| 90 | cache-a | cache-a |

只有 35 搬家，而且是从下线的机器交给它的后继。

**cache-d 加在 30。** 它从 cache-b 手里切走 `(20, 30]`，cache-b 还留着 `(30, 50]`。落点 25 的 key 从 cache-b 改到 cache-d；落点 35 仍在 cache-b。没有 key 从 cache-a 跑到 cache-c。

> **核心结论：** 从 `N` 台删掉 1 台，期望约 `1/N` 的 key 搬家；在 `N` 台之外加 1 台，期望约 `1/(N+1)` 的 key 搬家。搬走的 key 只进出这一台。

## 3. 两种常见变体

权重改变的是一台机器占多少个点。副本改变的是顺时针继续收集几台不同的物理机器。

### 3.1 带权重的环

机器容量不一样时，按权重分配虚拟节点。权重大的机器点更多，期望分到的 key 和权重成比例。

三台机器权重 `1 : 2 : 1`，每个权重单位放 50 个点：

| 机器 | 权重 | 点数 | 期望 key 比例 |
| :--- | ---: | ---: | ---: |
| cache-a | 1 | 50 | 25% |
| cache-b | 2 | 100 | 50% |
| cache-c | 1 | 50 | 25% |

查找规则不变，还是顺时针的下一个点。cache-b 的点更密，所以切到的小弧更多。

调整权重等于加减这台机器自己的点。cache-b 的权重从 2 降到 1，就删掉它一半的点；这些点后面的弧交给顺时针的下一台，cache-b 剩下的点以及另外两台的点都不动。这和上一节的再平衡是同一件事，只是一次只动一台机器的一部分点。

### 3.2 环上的副本

一份数据要放在多台机器上时，从 key 的主人开始顺着环走，收集 `N` 台不同的物理机器。虚拟节点交错之后，相邻的两个点经常属于同一台机器，所以已经选过的物理机器要跳过。

用第 1 节的环，落点 35 的 key 主人是 cache-b。三副本按顺时针就是：

| 顺序 | 机器 | 角色 |
| ---: | :--- | :--- |
| 1 | cache-b | 主副本 |
| 2 | cache-c | 下一台不同的物理机器 |
| 3 | cache-a | 再下一台，绕过 100 回到 cache-a |

cache-b 下线后，这份 key 的主副本改成 cache-c，副本列表只剩 cache-c 和 cache-a。已经在这两台上的副本不用重选；要补回第 3 份，得等环上还有别的机器。
